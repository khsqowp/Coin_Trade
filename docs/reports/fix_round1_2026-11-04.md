## 설계 판단과 남은 위험

- Binance 호출은 현재 표시 요청 스레드에서 실행되지 않는다. 전용 worker의 refresh flag가 엔드포인트별 중복 갱신을 막는다. Java 취소는 interrupt 신호다. 무시하는 임의의 주입 Fetcher 스레드는 종료를 강제할 수 없지만, HTTP 실제 경로는 connect/request timeout과 작업 전체 timeout으로 제한된다.
- `application.yml`과 소스에서 `server.tomcat.threads.max` 명시값은 찾지 못했다. 따라서 Tomcat 기존 기본/배포 설정은 변경하지 않았다. `/actuator/health`는 Binance 표시 서비스 락을 사용하지 않으나 Tomcat worker pool을 공유하므로, 다른 요청 전체가 worker를 소진하면 헬스 응답도 영향받는다. 이번 변경은 `/state`가 Binance 대기로 worker를 점유하던 원인을 제거한다.
- 현재 코드에서 격리 포지션의 리사이즈 증액은 포지션 모드를 바꾸지 않고 `set_leverage` 후 주문하므로 격리 상태를 유지한다. 격리 증거금이 부족하면 증액이 거부될 수 있고 기존 처리에서 리사이즈 오류로 기록된다. BCH/XRP가 다음 리밸런스에서 유지되면 격리 상태로 남는다. 교차로 전환하려면 해당 포지션 청산 후 신규 진입이 필요하다. 보유 포지션에 대한 직접 마진모드 변경 호출은 하지 않았다.
- 거래소별 수량 step 메타데이터가 없거나 잘못된 경우에는 주문량을 추정하지 않고 계획 오류로 남긴다. 신규 진입의 수량 산출 경로는 수정하지 않았다.

## 재작업 라운드 1 — 2026-11-04

### 리뷰 반영

- `BinanceDisplayService` stale 기준을 캐시 TTL과 분리했다. 계좌 stale 임계는 60초(TTL 20초의 3배), realized stale 임계는 3시간(TTL 1시간의 3배)이다. 실제 조회 실패, timeout, 워커 포화는 60초 백오프를 기록해 stale로 표시한다. 정상 30초 폴링만으로는 계좌가 stale이 되지 않는다.
- refresh worker는 최대 4개, 무대기 `SynchronousQueue`로 제한했다. 4개가 모두 점유되면 신규 갱신을 거절하고 60초 백오프를 둔다. 별도 단일 timeout 스케줄러가 10초(계좌)/60초(realized)에 flight를 해제한다. timeout을 무시하는 워커는 강제 종료할 수 없으며, 최대 4개 데몬 워커 슬롯이 계속 점유될 수 있다. 이 한계에서는 추가 스레드가 증가하지 않고 신규 갱신이 잠시 생략된다.
- flight 객체 동일성으로 timeout/완료 처리를 현재 요청에 한정했다. 워커 결과도 해당 flight가 현재일 때만 캐시에 반영한다. 따라서 timeout 후 복구한 새 요청을 늦은 워커가 지우거나 덮지 않는다.
- `BinanceDisplayService.java`와 `MomentumRotationStateController.java`의 압축된 계산/루프를 여러 줄로 풀었다. controller 계산 순서와 표시 데이터 규칙은 유지했다.
- 리사이즈의 `abs(delta) < min_cost` 조건을 step 보정 전에 적용해 `RESIZE-SKIP`한다. 최소 명목 미만 delta가 step 크기 때문에 주문으로 바뀌지 않는다. 그 밖의 수량 정밀도, 방향, reduceOnly 및 실행 순서는 변경하지 않았다.
