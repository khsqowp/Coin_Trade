# 코인 차트 예측 서비스 — 시나리오 & 요구사항 명세서 (v0.1, 2026-11-14)

상태: **요구사항과 일부 로컬 조사·검증이 진행된 상태.** 아래 §13의 진행기록은 당시 실행 보고이며, 현재 전체 테스트·운영·Linux 배포 상태를 보증하지 않는다. 이 명세는 코인 차트 분석·신호 알림 제품만 다루며 국장·미장 자동매매 제품은 [별도 명세](../kr-us-equity-trader/SPEC.md)로 관리한다.
참조 서비스: gptchart.ai (`/Users/user/Downloads/gptchart.ai.har`로 API 구조 분석).

## 1. 목적

사용자가 차트 이미지를 보내면, AI가 캔들·추세·지표·추세선·피보나치 등을 분석해 **앞으로의 예상 경로를 차트 위에 그려 이미지로 돌려준다.** 이후 예측이 실제로 맞았는지 자동 채점하고, 오답노트로 예측 로직을 개선한다.

## 2. 사용자 시나리오

| # | 시나리오 | 입출력 |
|---|---|---|
| S1 | 이미지 예측 | Telegram(CoinBot)으로 차트 스크린샷 전송 → 심볼/분봉/가격축 인식 → 분석 → 예상 경로 오버레이 이미지 + 요약 텍스트 회신 |
| S2 | 심볼 직접 요청 | "BTCUSDT 5m" 텍스트 → 서버가 캔들을 직접 수집해 같은 파이프라인 실행 |
| S3 | 자동 채점 | 예측 시점 + 예측 구간이 지나면 실제 캔들과 비교 → 적중/오답 기록, 요청자에게 결과 알림 |
| S4 | 오답노트 | 누적 오답을 유형별로 분류 → 규칙/프롬프트 개선안 → 재검증 |
| S5 | 실시간 신호 감시 | 사용자가 등록한 코인 또는 감시 목록을 서버에서 계속 관찰 → 사전 검증된 급등·급락 후보만 차트 이미지와 함께 Telegram으로 발송 |

## 3. 참조 서비스(gptchart.ai)에서 확인된 구조

HAR 분석(키·토큰은 사용·기록하지 않음):

- **입력은 이미지가 아니라 OHLC JSON.** `POST /api/canvas/chat`에 `symbol`, `interval`, `market`, 최근 캔들 배열(`time/open/high/low/close`), 대화 이력을 보낸다.
- 캔들 소스: `GET /api/canvas/candles?symbol=BTC-USDT&interval=1H&market=crypto`.
- **출력은 SSE 스트림**: `thoughts`(추론 진행), `tool`(`clear_drawings` 등 도구 호출), `drawings`(구조화된 도형 목록), `content`(마크다운 분석문).
- 도형 타입: `pattern`(채널 등), `trendline`, `marker`(BOS/LH/LL), `zone`(저항/지지 구간), `horizontal`(진입/손절/목표), 그리고 `projected:true, arrow:true`인 **예상 경로 폴리라인**(시간·가격 점 목록).
- 분석문 구성: 구조 → 방향/편향 → 설정(진입·손절·목표·손익비) → 무효화 조건·위험.
- 시사점: 우리도 **이미지는 입력 인터페이스일 뿐, 내부 분석은 캔들 JSON으로** 하는 것이 정확하고 저렴하다. 이미지 → 캔들 복원이 불안정하면 심볼/분봉만 읽어 거래소 API로 같은 구간을 다시 받는다.

## 4. 기능 요구사항

**수집·입력**
- FR1. 이미지에서 심볼·분봉·마지막 가격·시간축을 인식한다(AI 비전). 인식 실패 시 사용자에게 되묻는다.
- FR2. 분석 데이터는 공개 시세만 사용하며 주문 권한·개인 거래소 키를 쓰지 않는다. 실시간 감시는 스트림 또는 기존 market-data 어댑터를 우선 검토하고, 과거 구간·재접속 누락분은 공개 캔들 API로 보충한다. 공급자와 어댑터는 확정 전까지 미정이며, 고빈도 REST 폴링을 기본 설계로 삼지 않는다. 이미지와 수집 캔들이 어긋나면 수집 캔들을 기준으로 삼고 불일치를 기록한다.
- FR3. 대상은 사용자가 지정한 코인 또는 거래량 상위 50~100개 중 선별한 USDT 무기한 선물 심볼이다. 거래소 메타데이터상 COIN형 underlying만 포함하고 주식·원자재 토큰은 제외한다. 초기 시험은 최소 10종으로 시작.

**분석 지표 (결정적 계산, LLM이 아닌 코드가 산출)**
- FR4. 캔들 패턴(장악형, 핀바, 모닝/이브닝스타, 도지 등), 추세 지표(EMA/SMA, MACD, RSI, ADX, 볼린저, ATR, VWAP), 거래량 프로파일, 스윙 고저점(HH/HL/LH/LL), BOS/CHoCH.
- FR5. 추세선·채널·수평 지지/저항 구간 후보 자동 산출, 피보나치 되돌림/확장 레벨.
- FR6. TradingView Pine 스크립트의 **로직을 참고해 Python으로 재구현**한다. 라이선스가 불분명한 스크립트는 복사하지 않는다.
- FR7. 위 지표를 구조화 JSON으로 LLM에 제공하고, LLM은 해석·시나리오·경로를 만든다. 지표 값을 LLM이 직접 계산하지 않는다(환각 방지).

**예측 출력**
- FR8. 예측은 **고정 스키마**로 저장한다: 심볼, 시장(USDT 무기한 선물), 분봉, 생성 시각, 앵커(마지막 확정 캔들 시각), 방향(상/하/횡보), 보정 신뢰도(0~1), 패턴·시장구조(HH/HL/LH/LL, BOS/CHoCH 등), 추세선·지지·저항 구간, 확인 진입 조건/가격 구간, 무효화·손절 가격, 1·2차 목표 및 목표 구간, 예상 경로(시간·가격 점 목록), 예측 구간, 목표/손절 선도달 확률과 데이터·모델 버전.
- FR9. 위 정보를 차트 위에 표시한 PNG와 요약을 Telegram으로 회신한다. 그림은 신호의 기준 시각·현재가·분봉·방향, 구조/패턴, 지지·저항·진입 확인 조건, 무효화·손절, 1·2차 목표, 예측 경로·기간을 구별해 표기한다.
- FR10. 예측 스키마는 **저장 후 수정 불가(append-only)**. 채점 후 예측을 고치지 않는다.
- FR13. 신호 생성 시점의 현재가와 최신 확정 캔들 시각을 함께 기록한다. 목표/손절에 이미 먼저 닿았거나, 예측 구간이 지났거나, 데이터 지연·가격 불일치가 허용치를 넘으면 새 진입 신호로 보내지 않는다. 과거 신호를 차트로 재생할 때는 당시 가격과 현재 가격을 명확히 분리한다.

**예측 구간**

| 분봉 | 예측 구간 | 예측 후 채점 시점 |
|---|---|---|
| 1m | 10~20분 | 20분 뒤 |
| 5m | 50~100분 | 100분 뒤 |
| 30m | 300~600분 | 600분 뒤 |
| 60m | 600~1200분 | 1200분 뒤 |

**채점·개선**
- FR11. 채점기는 결정적 코드다(LLM 판단 금지). 예측 구간 종료 후 실제 캔들로 지표를 계산한다.
- FR12. 오답노트는 오답을 유형으로 분류한다(방향 오류, 타이밍 오류, 변동성 과소/과대, 무효화 미준수, 지표 오독 등). 개선안은 **다음 검증 세트에서** 평가한다.

## 5. "정확도 80~90%"의 정의 — 먼저 확정해야 하는 항목

목표 수치는 **측정 정의 없이는 의미가 없다.** 아래 중 무엇을 80~90%로 볼지 사용자 확정이 필요하다. 제안은 다음과 같다.

| 지표 | 정의 | 비고 |
|---|---|---|
| M1 방향 적중률 | 예측 구간 종료 시점 가격이 예측 방향으로 기준가 대비 마감 | 횡보 임계값(±0.1×ATR 등) 필요 |
| M2 목표 도달률 | 구간 내 목표 구간에 터치(무효화 전) | 무효화 우선 규칙 필요 |
| M3 경로 오차 | 예측 경로 vs 실제 종가의 MAE/ATR 정규화, 방향 일치 구간 비율 | 연속값이라 "맞다/틀리다"가 아님 |
| M4 신뢰도 구간 적중률 | 신뢰도 ≥ 임계값인 예측만 집계 + **커버리지(전체 중 비율)** 함께 보고 | 아래 참고 |

- **단순 방향 적중률은 무작위가 약 50%, 단기(1~60분봉)에서는 지속적으로 55%를 넘기기 어려운 것이 일반적이다.** 전체 예측에서 80~90%는 현실적인 목표가 아닐 가능성이 높다.
- 따라서 **M4(높은 신뢰도 신호만 선택, 나머지는 "예측 보류")** 로 정의하는 것을 제안한다. 이 경우 80~90%가 성립할 수 있으나 커버리지가 작아지므로 **정확도와 커버리지를 항상 함께 보고**한다.
- 모든 지표는 **베이스라인 대비**로 본다: ① 항상 직전 방향 유지(모멘텀) ② 무작위 ③ 항상 횡보. 베이스라인을 못 이기면 개선으로 치지 않는다.
- 수수료·슬리피지를 고려한 손익 지표(R-multiple, 기대값)는 별도로 기록한다. 적중률이 높아도 손익비가 나쁘면 의미가 없다.

## 6. 검증 방법과 과적합 방지

**6.1 LLM 사전학습 오염(가장 중요)**
- LLM은 과거 가격 이력을 학습했을 수 있다. 과거 구간 리플레이 결과는 **기억에 의한 적중**으로 부풀려질 수 있다.
- 대응: ① 검증용 데이터는 **모델 지식 컷오프(2026-06) 이후** 구간만 사용 ② 심볼명·날짜를 가리는(마스킹) 대조 실험 ③ 실시간 전진(forward) 테스트를 최종 판정으로 사용.

**6.2 데이터 분할**
- 개발(튜닝)/검증(고정)/최종(봉인) 3구간. 오답노트는 개발 구간에서만 사용하고, 검증·봉인 구간은 개선 중 열람하지 않는다.
- 종목 분할: 개선에 쓰는 종목과 평가 종목을 분리(종목 과적합 방지). 순차 테스트: 한 종목이 전체 점수를 좌우하지 않게 종목별 점수를 따로 보고.
- 룩어헤드 금지: 예측 시점 이후 캔들, 이후에 확정되는 지표(미완성 캔들, 후행 피벗 확정)를 입력에 넣지 않는다. 미래 변조 테스트(prefix 불변성)를 자동화.

**6.3 다중 비교**
- 수정·재시험 횟수(trial count)를 기록한다. 시험 횟수가 늘수록 우연히 좋은 결과가 나올 확률이 커지므로, 최종 판정은 봉인 구간 1회로 한다.
- 최종 적중률은 표본 수와 신뢰구간(예: Wilson 95%)과 함께 보고한다. 표본이 작으면 "달성"으로 표기하지 않는다.

**6.4 표본 규모(초안)**
- 종목 10개 × 분봉 4개 = 40개 셀. 셀당 최소 N건(권장 100건 이상, 시간 독립 샘플)을 확보한다.
- 상관 방지: 같은 종목·분봉의 겹치는 예측 구간은 독립 표본으로 세지 않는다(구간 간격 ≥ 예측 구간).
- 이 규모에서는 LLM 호출이 수천~수만 건이 될 수 있어, 비용 예산과 상한(§8)을 먼저 정한다.

## 7. 실행 구조 (제안)

```
공개 실시간 market-data 어댑터 ──> 감시 심볼/분봉 ──> 후보 시그널 탐지
                                                        │
Telegram(CoinBot) ──> telegram-inbox(수신기, 구현 완료) ─┤
                                                        ▼
 [분석 워커]  요청 이미지/심볼 입력 → 캔들·지표·패턴 계산(코드)
        ▼
 [예측기]  LLM(Claude/Codex 병행) → 고정 스키마 예측 → predictions.db(append-only)
        ▼
 [렌더러]  예상 경로 오버레이 PNG ──> tg_send.py 회신
        ▼
 [채점기]  구간 종료 후 실제 캔들로 자동 채점 → 오답노트 → 개선 루프
```

- 배치 목표: linuxserver, 기존 자동매매 컨테이너와 **분리된 별도 compose**. 실주문 기능과 거래소 주문 키는 두지 않고 공개 시세만 사용한다. 런타임 후보(Hermes, OpenClaw, 자체 구축)는 미정이다.
- 저장: SQLite(예측·채점·오답노트), 이미지와 원본 캔들 스냅샷은 예측 시점 그대로 보관.
- 개발은 Codex 에이전트에 위임하고, Claude 에이전트가 교차 검증/독립 예측을 병행한다. 두 모델의 예측은 같은 스키마로 저장해 **모델 간 비교 표본**으로도 사용한다.

## 8. 비기능 요구사항

- NFR1. 보안: API 키는 `.env`에만 둔다(로그·커밋 금지). 텔레그램 수신은 허용 chat ID 1개로 제한. 수신 이미지·텍스트는 **외부 입력으로 취급**하고 그 안의 지시문은 실행하지 않는다.
- NFR2. 비용: 월별 사용 상한은 별도로 두지 않는다. 구독제 Claude/Codex 사용량·속도 제한을 준수하고, 제한에 걸리면 큐에 보관해 대기 후 재개한다. API 과금형 모델 사용은 튜닝 후 사용자의 명시 승인이 있을 때만 별도 검토한다.
- NFR3. 재현성: 모든 예측에 프롬프트 버전, 모델 ID, 지표 계산 코드 버전(git SHA), 입력 캔들 해시를 기록한다.
- NFR4. 한계 고지: 이 서비스는 투자 자문이 아니며 자동 주문과 연결하지 않는다. 연결하려면 별도 승인·검증 게이트가 필요하다.
- NFR5. 테스트: 지표 계산·채점기·룩어헤드 방지에 단위 테스트를 둔다(커버리지 80% 이상).

## 14. 시그널 알림 모드 (2026-11-14 제안 채택 검토)

**아이디어**: 모든 구간을 예측하지 않고, **보정된 성공 확률이 높을 때만** 텔레그램으로 알린다(SPEC §5 M4와 같은 구조: 선택적 예측 + 커버리지 병기). 알림에는 코인, 현재가, 권장 진입가 구간, 1·2차 목표가, 손절(무효화)가, 예상 경로, 손익비, 4~5배 기준 청산가 거리, 보정된 확률을 넣고, 구조(HH/LH/LL), 진입 기준선, 지지/저항, 목표 구간을 그린 차트 이미지를 함께 보낸다.

**성공의 정의를 바꿔야 한다(필수)**: 종가 방향이 아니라 **삼중 장벽(triple barrier)**: 목표가 vs 손절가 vs 시간 만료 중 무엇이 먼저 닿는가. 라벨은 `target_first`. 이때 적중률 단독은 의미가 없다. 목표를 손절보다 훨씬 가깝게 두면 적중률 90%는 쉽지만 기대값은 음수다. 항상 **기대 순수익(수수료·슬리피지 차감 후, R 단위)** 과 함께 본다. 본전 승률 p* = (S + c) / (S + T) (S 손절폭, T 목표폭, c 왕복 비용, 모두 같은 단위).

**알림 게이트(모두 충족 시에만 발송)**
1. 보정된 P(target_first) ≥ 사전 고정 임계값(워크포워드로 보정, 모델이 말한 신뢰도가 아니라 실현 빈도로 보정)
2. 기대 순수익 > 0 이고 T ≥ 비용의 k배(비용 벽 통과)
3. 거래량 상위 N개와 최근 변동성 필터. 호가 깊이·슬리피지·체결 가능성은 현재 사용자 결정에 따라 평가하지 않는다.
4. 종목별 쿨다운, 일일 상한, 시장 급변(BTC) 구간 억제

**운영**: 모든 알림은 append-only 로그에 남기고 구간 종료 후 자동 채점해 **실현 적중률/기대값을 롤링으로 공개**한다. 실현이 보정 기대치보다 유의하게 낮으면 자동으로 알림을 멈춘다(드리프트 가드). 이 로그가 곧 **봉인(라이브 전진) 검증 데이터**가 된다.

**단계**: ① 삼중 장벽 라벨 탐침(상위 50 종목, 변동성 필터, 레버리지 4·5배, 비용 민감도)으로 보정된 고확률 구간이 존재하는지 확인 → ② 존재하면 섀도우 모드(알림 발송 + "검증 중" 표기, 거래 신호로 취급하지 않음)로 며칠~수 주 누적 → ③ 사전 정한 기준을 넘으면 정식 알림. ①에서 보정된 구간이 없으면 알림 기능을 만들지 않는다(엣지 없음으로 기록).

**한계/주의**: 투자 자문이 아니며 자동 주문과 연결하지 않는다. 고확률 신호는 드물 수 있고, 하루 0건일 수도 있다. 그것이 정직한 결과다.

### 14.1 정정 (2026-11-14, 사용자 지시 반영)

- 알림 기준: 목표가에 먼저 닿는 비율(채점용)이 **75% 이상**일 때만 발송. 단, 수수료를 뺀 기대 순수익이 양수여야 한다(승률만으로 판단하지 않는다).
- 단순화: 소액 운용이라 **슬리피지·호가 깊이·체결 가능성 변수는 고려하지 않는다.** 고정 수수료(왕복 약 0.1%)만 반영한다. 레버리지 4~5배 기준 수익을 본다.
- 목표: "수익이 나느냐, 크게 나느냐" 두 가지만 본다. 75% 이상 + 순수익 양수 + 순수익 크기 순으로 신호를 고른다.
- 용어: 삼중 장벽은 **채점 방법**이다(알림 이후 목표가/손절가 중 먼저 닿은 쪽을 기록). 거래 방식이 아니다.
- (2026-11-14) 손익비 확정: 목표:손절 = 2:1 ~ 4:1 (손절은 목표의 1/2 ~ 1/4). 알림 기준은 "목표에 먼저 닿는 비율 ≥ 75%" 하나. 참고: 무작위 기준선은 2:1에서 약 33%, 4:1에서 약 20%.

### 14.2 차트 알림의 목적과 이미지 예시 반영

- 이 제품은 사용자의 수동 롱/숏 의사결정을 돕는 분석·알림 시스템이다. 사용자가 레버리지와 주문 여부를 결정한다. 기존의 8:8 자동매매 시스템과 주문을 주고받거나 포지션을 변경하지 않는다.
- 첨부 차트는 시각적 출력 예시이며 그 안의 숫자·예측은 검증된 신호로 간주하지 않는다. 구조/패턴, 저항·지지, 진입 확인선, 무효화·손절, 목표 구간, 예상 경로와 시간 범위를 표시하는 레이아웃만 요구사항으로 반영한다.
- 이미지 예시처럼 현재가가 이미 목표 구간을 넘어선 경우에는 목표 선도달로 판정하고 신규 진입 알림을 금지한다. 시그널은 반드시 앵커 시각, 데이터 시각, 현재가, 만료 시각을 함께 갖는다.

## 15. 운영 아키텍처 — 규칙 틀 + AI 판단 (2026-11-14)

최종 운영 형태는 완전 결정적 규칙 시스템이 아니다. **고정된 기준점·출력 포맷(§14 알림 게이트, 스키마)** 위에서 실제 판단(패턴 해석, 확신도 산정, 문구 작성)은 **AI API 키 기반 에이전트**가 하고, 결과는 Telegram(`khsqowp_CoinBot`)으로 전달한다.

- API 키 사용은 §4 결정대로 **튜닝 완료 + 사용자 명시 승인 후에만** 연다. 그 전까지는 구독제 에이전트(Claude/Codex)로 규칙과 임계값을 검증한다.
- **운영 목표 위치는 linuxserver다.** Oracle 서버는 역할 분리 완료 — 2026-11-14에 트레이딩 리서치 파이프라인(`hermes` 등 8개 컨테이너)을 전부 `restart=no`로 멈췄고, **다시 살리지 않는다.** 이 코인봇 프로젝트와 Oracle은 앞으로도 무관하다.
  - 에이전트 런타임 후보: openclaw / Hermes(NousResearch agent framework) / 자체 구축. **미정.** 어느 쪽을 택해도 linuxserver에 새로 설치해서 쓴다 — Oracle의 멈춘 `hermes` 컨테이너를 재사용하지 않는다(이름만 같을 뿐 별개 배포).
- 운영 중 지속 최적화는 **과적합 방지 틀 재사용**: 튜닝은 개발 구간에서만, 검증/봉인 구간은 판정 전용. 일정 주기 워크포워드 재검증 + 드리프트 가드(§14 운영절)로 실현 성과가 기대치보다 유의하게 낮으면 자동 알림 중단. 규칙/프롬프트 변경마다 버전·시험 횟수를 `trials.sqlite`에 누적 기록.

## 16. 제품 경계 및 사본 관리

- 이 문서는 코인 차트 분석·신호 알림 제품만 규정한다. 국장·미장 자동매매는 별도 제품이며 이 문서의 무주문 원칙을 그 제품의 주문 정책에 전이하지 않는다.
- 기준 사본은 로컬 `docs/chart_predictor/SPEC.md`다. 동일 내용의 운영 사본은 Linux 서버의 `~/CODE/Coin_Trade/docs/chart_predictor/SPEC.md`에 둔다. 동기화 시 기준 사본과 SHA-256을 대조하고, 서버에는 문서만 복사한다. 이 절은 애플리케이션 배포나 서비스 재시작을 승인하지 않는다.
