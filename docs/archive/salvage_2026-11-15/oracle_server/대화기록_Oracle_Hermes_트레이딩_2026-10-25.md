사용자는 원래 서버를 마이그레이션하려 했지만 다른 것을 옮기기로 했으므로 기존 컨테이너와 관련 자원을 내리고 지우라고 요청했다. SSH 접속 후 실행 컨테이너는 0개, 이미지 13개, 볼륨 10개가 발견됐다는 보고가 나왔다. 볼륨이 각 4KB 이하의 테스트 상태로 판정됐고, 컨테이너·이미지·볼륨·빌드 캐시를 지워 약 1.5GB를 회수했다고 보고됐다. 현재 로그만으로는 원격 삭제가 실제로 수행됐다는 점을 이 대화 밖에서 독립 확인할 수 없다.

### 2. 보안 진단 및 업데이트

사용자는 Codex 에이전트로 Oracle Linux 보안 재진단을 요청했다. 대화상 점검 대상은 Oracle Linux 9.8 aarch64였고, SSH 설정, fail2ban, 자동 업데이트, sysctl, rpcbind, Docker 및 로그를 살폈다고 보고됐다. SSH 키 로그인 관련 설정을 적용하고 새 SSH 세션 접속도 확인했다는 기록이 있다. 이후 에이전트 보고서의 불명확한 항목을 직접 재확인했다고 했다.

최종적으로 “침입 흔적 없음”, fail2ban 및 dnf-automatic 활성, SSH 접속 정상이라고 보고됐다. 이는 로그와 설정 범위의 점검 결과이며, 침해가 없었다는 포괄적 증명은 아니다. 이어 사용자가 버그 수정 업데이트만 요청했고, Python 패키지 6개 업데이트, 재부팅 불필요, sshd/fail2ban/firewalld/docker 활성이라고 보고됐다. 80/443을 닫을지 묻는 상태에서 사용자가 웹 사용 예정이라며 그 포트 변경을 임의로 하지 말라고 분명히 했다.

### 3. 거래 연구 파이프라인의 첫 버전

사용자는 Hermes를 코인·미국 주식·한국 주식 거래 전문가로 키우고, Hermes 멀티에이전트에서 작업 모델은 저가형, 검토·관리 모델은 중간급으로 나누고 싶다고 했다. Binance 사용, 코인과 주식 병행, Telegram 이용을 선택했다. 실거래는 금지하고, `80/443`은 유지하라는 제약도 명시했다.

Freqtrade는 코인 전용이라는 설명 뒤, 서버에 dry-run 구성을 만들었다고 보고됐다. `~/trading/`, Binance 공개 시세, 가상 1,000 USDT, BTC/ETH/SOL/BNB 페어, 샘플 RSI 전략, API/UI의 localhost 바인딩, 무작위 UI 자격증명 파일(권한 600), 실거래 키 미사용을 보고했다. Hermes 이미지도 받았지만 초기에는 API 키와 Telegram 설정이 남아 있었다. 주식은 별도 KIS/Alpaca 연동이 필요하다고 구분했다.

사용자는 `/home/opc/trading/.env`에 Binance, KIS 모의, TOSS 실거래용 키가 있다고 알리며, 실거래는 아직 금지라고 재확인했다. 파이프라인은 데이터 저장소 → Agent A(시장분석·가설·연구계획) → Agent B(전략 코드·실행·테스트) → Agent C(독립 검증·반증) → 백테스트·통계 판정의 순서로 요청했다. 역할은 Researcher, Engineer, Auditor, 비LLM Risk Engine으로 나눴고, 정확성·코드 품질·오류 탐지·재현성·비용을 평가하는 작은 벤치마크를 제안했다.

첫 Codex 작업은 약 $0.15가 들었다는 보고가 나왔다. API 중계 제한으로 Hermes 자체 멀티에이전트 대신 Python 오케스트레이터 `~/trading/pipeline/driver.py`를 만들었다고 했다. Binance 공개 OHLCV 및 KIS 모의 데이터 수집, 출처·시각·해시, Auditor와 Risk Engine 게이트, 미래 참조 오류 탐지, 반복 재현성 시험을 구성했다고 보고했다. TOSS 키는 로드하지 않고 주문 API도 호출하지 않았다고 했다.

여기서 중요한 비밀정보 사고가 보고됐다. `.env`의 일부 줄이 `KEY: value` 형식이라 키 이름만 확인하려던 명령이 봇 토큰 값을 출력했고, 출력이 에이전트 로그/외부 모델 세션에 포함됐다고 했다. 이후 사용자가 `.env` 권한 처리를 지시했고 `~/trading/.env`, `pipeline/secrets/kis.env`, `pipeline/secrets/llm.env` 모두 권한 600으로 확인했다는 보고가 나왔다. 다만 토큰 회전 여부는 끝까지 완료로 확인되지 않았고, 후속 안내에서는 교체가 미완료 상태로 반복 언급됐다. 이것은 이 대화에서 해결되지 않은 보안 후속조치다.

후속 구현에서는 Coin_Trade 전략 참고 라이브러리, ablation 검증, Telegram 단방향 알림, Freqtrade 후보 등록 경로를 추가했다고 보고했다. 테스트 79개 통과, 15개 전략 요약, 알림 API 응답 4건 200을 보고했지만 실제 휴대전화 도착 여부는 사용자 확인이 필요했다. 첫 통합 백테스트는 BTC/ETH/삼성전자 후보가 MDD, 거래 수, dead rule, 표본 외 성능 또는 허용 목록 조건으로 모두 차단됐다고 했다. SK하이닉스는 실행하지 않았다.

### 4. 전략 방향과 시장 데이터 요구사항 확장

사용자는 Telegram 메시지 순서가 예상과 일치했다고 확인하고, 보호 규칙의 의미를 물었다. 전략은 시장 추세·가속·뉴스·정책·전세계 이벤트에 따라 동적으로 선택되길 원했다. 한국 주식은 대형주와 급등 추격을 원했고, 급등 진입 후 +5% 익절 또는 -3% 손절 규칙을 설명했다. “토큰 $5를 주고 다 쓰면 죽는” 생존형 에이전트 아이디어도 물었다.

응답은 LLM에게 매 순간 주문 신호를 내게 하기보다 시장 국면 분석과 고정 전략 풀 선택을 맡기고, 실행 및 위험관리는 결정론적 코드로 제한하자는 설계를 제안했다. 뉴스는 과거 데이터 백테스트에 섞지 않고 현재부터 타임스탬프를 쌓아 포워드 평가하자는 판단이 나왔다. 국내 급등 추격은 일봉으로 목표·손절 순서를 알 수 없고 분봉 및 체결 현실성 문제가 크다는 한계가 기록됐다. 생존형 구상은 모의 계좌 아레나, 비용 차감, 고정 위험 한도, 성과 저조 에이전트 퇴출로 제한하자는 제안이었다.

사용자는 뉴스 소스 2~5개 선정과 다음 단계를 승인했다. 제안 소스는 GDELT, Federal Reserve RSS, CoinDesk/Cointelegraph RSS, 연합뉴스 경제 RSS, CNBC/BBC Business RSS였다. 추가 비뉴스 자료로 Fear & Greed, Binance 펀딩비·OI를 거론했다. 최초 Codex 호출은 로컬 샌드박스에서 SSH가 막혀 시작하지 못했고, 사용자는 SSH 직접 구현으로 고정했다. 그 뒤에는 수집기, 국면 에이전트, 전략 풀, 합성 급락으로 stop 검증, arena smoke test, 인젝션 테스트를 지시한 것으로 기록됐다.

코인 전략 선호가 구체화됐다. 사용자는 경험상 추세·차트 패턴·BTC 흐름·청산가 히트맵을 활용한 추종이 가장 수익성이 좋았다고 말했다. 대화에서는 다중 시간대 추세, 코드 기반 차트 패턴, BTC 레짐 피처를 제안했다. ### 5. Hermes 실제 서버 배치 및 Telegram 연결

파이프라인 작업과 병행해 Hermes를 설정했다. 기본 컨테이너 실행 방식은 TTY가 없는 서버에서 약 20초마다 재시작하며 CPU 한 코어를 소모했다. 이를 발견하고 `gateway run`으로 바꾼 뒤 CPU 약 0.4%, 메모리 약 250MB로 안정됐다고 보고했다. Anthropic API 호출 스모크 테스트는 `OK`였다고 했다. 이 단계에서 Hermes는 별도 `hermes.env`(권한 600)를 사용했고, 거래소·TOSS 키는 컨테이너에 전달하지 않았다고 보고됐다.

처음에는 노출 이력이 있다고 판단한 기존 COINBOT 토큰 대신 새 Telegram 봇을 권했다. 사용자가 “코인봇 써”라고 지시한 뒤 해당 토큰으로 연결했다고 보고했다. 허용 사용자는 사용자 ID 하나로 제한했다고 했고, Telegram polling 연결을 확인했다. 모델은 본체/관리 Claude Sonnet 5.5, 하위 작업 Claude Haiku 5.5, 동시 3개·최대 60턴으로 설정했다고 보고됐다. 단, 위험 명령 승인 동작은 확인하지 못했고 실제 Telegram 테스트가 필요하다고 명시됐다.

### 7. 시간대 및 2차 연구 결과

사용자는 서버 시간을 한국 시간으로 맞추라고 했다. 결과 보고에 따르면 호스트는 이미 Asia/Seoul 및 NTP 정상 상태였고, 코드에서 한국 장 시간과 미국 서머타임 처리를 보완했으며, 예산 일일 리셋은 KST 자정으로 바꿨다. 기록 타임스탬프는 해시 체인을 보존하기 위해 UTC로 유지했고, Hermes 컨테이너에 `TZ=Asia/Seoul`을 넣었다. Freqtrade, 방화벽, SSH는 건드리지 않았다고 했다.

2차 연구는 테스트 176개 통과, 실거래 후보 없음으로 보고됐다. Binance 일반 등급 선물 수수료를 maker 0.02%, taker 0.05%로 두되 공식 자료상의 예시값이므로 파라미터 처리했다고 했다. 슬리피지 0.02% 및 유지증거금 0.5%는 공식 근거 없는 가정이라고 밝혔다. 기간·타임프레임 분석에서는 짧은 봉에서 거래비용이 컸고, 가장 좋아 보인 전략도 시도 횟수 보정 후 통계적으로 유의하지 않았다. LLM 역할 실험은 변동성 타깃이 약간 개선됐을 뿐 규칙으로 충분했고, 이벤트 리스크 태깅 정도만 포워드 검증 가치가 있다고 평가했다.

포워드 후보 10개를 0일차로 등록했다고 보고했다. 기준은 28일 이상, 20거래 이상, LLM 비용 차감 후 순이익 플러스, 샤프 0.5 이상, MDD 15% 이하 등이었다. 스케줄러는 하루 $0.30, 워치독은 60초마다 점검, 일일 Telegram 요약은 08:00 KST라고 했다. 사용자가 실제 Binance 수수료 화면을 붙여넣은 뒤, 화면이 현물 표이고 Regular 사용자이며 BNB 할인 스위치는 켜져 있어도 BNB 잔액이 0이라 할인 미적용으로 정리했다. 선물은 별도 일반 등급 수수료 가정으로 분리했다.

### 8. 소액 로테이션 연구, Hermes 질의 기능, 예산 인센티브

사용자는 LLM 일일 $0.30 상한에 동의했다. 당시 계정에 약 128.883 USDT가 남았고, 향후 실거래 때는 이를 전부 쓸 생각이라고 했지만 “지금은 백테스트”라고 재차 강조했다. 원하는 아이디어는 보유 종목을 추적하다 하락이 계속되고 손실 확대가 예상되면 손절 후 새 종목으로 교체하는 로테이션이었다. 리밸런싱 주기는 1시간/몇 시간/1일 또는 시장 상황에 따라 유동적일 수 있다고 했다. Hermes에 파이프라인 결과를 채팅처럼 질의하고, 수익이 지속되면 스케줄러 예산을 늘릴 수 있다는 동기부여 조건도 문서화하라고 요청했다.

라운드 3은 백테스트/모의 연구 전용으로 계획됐다. 별도 `crypto_small_rotation` 프로파일에서 128.88 USDT, 기본 1배 롱, 2~3배 민감도, 주문 최소 단위·수수료·펀딩·청산을 비교하도록 했다. 기존 위험 기준은 바꾸지 않고, 사용자의 실거래 계정 로직과 연결하지 않으며 실거래 전환은 별도 승인 없이는 금지라고 명시했다. Hermes는 정제된 요약만 읽기 전용 마운트하고 원본 DB·뉴스·키는 주지 않는 설계였다. 예산 인센티브는 $0.30→$0.60→$1.00 단계, 성과 기준 충족 시 제안만 하고 실제 승인 전에는 상한을 바꾸지 않는 구조로 정했다.

Codex 세션 제한으로 작업이 중단됐지만, 재개 후 서버 기록상 다수 작업이 완료돼 최종 검증을 이어갔다고 보고했다. 마지막 결과는 66개 로테이션 변형 중 게이트 통과 0개였다. 단일 종목 변형의 손실과 낙폭이 매우 컸고, 3종목 분산은 상대적으로 나았지만 MDD 중앙값 81.7%로 위험했다. 최고 수익 변형은 시작 시각을 12시간 이동하면 샤프가 크게 무너졌고, 다중 시도 보정 DSR 최고 0.31로 기준 0.90에 못 미쳤다. BTC·ETH 단순 보유도 해당 기간 마이너스였으며, Coin_Trade 모멘텀 상위 3개도 MDD 79.4%였다고 했다. 이 자료와 기간의 한계로 신규 전략을 검증했다고 볼 수 없고, 오히려 과최적화·시작 시점 민감성·상장 생존 편향을 경고했다.

Hermes 질의는 10개 질문 테스트 통과로 보고됐다. 국면·포워드·예산·수집기 요약에 근거해 답했고, 주문·예산 인상·키 요청·종목 추천은 거절하며 인젝션 텍스트를 따르지 않았다고 했다. 파일 마운트는 읽기 전용이었다. 다만 파이프라인 외 질문은 Hermes 자체 웹 검색으로 답할 수 있다고 밝혀졌으므로 “질의 전부가 파이프라인 자료만 근거”라는 보장은 없다. 실제 Telegram 대화 테스트는 사용자 몫으로 남았다.

예산 인센티브 정책은 28일 이상·20건 이상·비용 차감 순수익 플러스·샤프 0.5 이상·MDD 15% 이하·벤치마크 초과 등의 기준을 제안 조건으로 삼았다. 에이전트가 직접 예산을 변경하지 못하고 호스트의 `budget.sh approve`를 사용자가 실행해야 한다고 보고했다. 2026-11-22가 가장 빠른 제안 가능 시점이라는 설명도 있었다.

## 확정된 사용자 의도와 제약

1. 목표는 당장 자동 실거래를 하는 것이 아니라, Oracle 서버에서 Hermes와 연구 파이프라인을 유지하고 몇 주간 백테스트/포워드 모의 기록을 쌓는 것이다.
2. 코인과 한국·미국 주식을 함께 연구한다. 코인은 상대적으로 빠른 기회도 허용하지만 타임프레임을 고정하지 않고 시장 조건에 따라 가변적으로 연구한다. 주식은 더 긴 보유도 가능하다.
3. 사용자 경험상 유효했던 코인 단서는 추세, 차트 패턴, BTC 흐름, 청산가 히트맵이다. 청산 히트맵 자동화는 REA가 아니라 공식·허용된 소스 또는 명시적 근사 지표만 대상으로 한다.
4. 국내 급등 추격 아이디어는 진입 후 +5% 익절/-3% 손절이지만, 분봉과 체결 제약을 반영해 검증해야 한다.
5. 실거래 키/주문 사용은 금지된 상태다. 사용자가 미래 실거래 희망을 말한 것은 현재 실거래 승인으로 해석하면 안 된다.
6. Oracle의 80/443 포트는 웹 서비스 용도로 보존한다. 포트, SSH, 시스템 보안 설정 변경은 요청 범위를 확인해야 한다.
7. LLM 자동 스케줄러 예산은 하루 $0.30에 동의했다. 성과 기반 예산 증액은 제안 조건이며 자동 증액 권한이 아니다.
8. Hermes는 텔레그램으로 질의할 수 있게 하되, 파이프라인 결과 접근은 정제·읽기 전용 범위로 제한하려는 의도다.

## 현재 맥락에서 중요한 결론

- 이 대화의 중심은 “AI가 수익을 보장하는 트레이더” 구축이 아니다. 현재 보고된 모든 전략 게이트가 BLOCK이며, 연구 결과는 유의미한 후보를 확보하지 못했다. 핵심 작업은 안전한 데이터 수집, 재현 가능한 연구, 여러 주의 포워드 관측, 비용·위험 포함 평가다.
- LLM의 직접 매매 권한은 설계에서 배제됐다. LLM은 시장 요약/이벤트 위험/연구 보조 영역에 두고, 리스크와 주문 경로는 결정론적 구성요소 및 사람 승인으로 통제하려는 흐름이다.
- “전액 사용” 표현은 사용자가 미래 실거래 자금 의향을 언급한 것이지, 현재 서버에 주문 기능을 켜라는 지시가 아니다. 대화 내에서 현재 실거래 금지라는 조건이 반복적으로 확인됐다.
- 사용자가 불만을 표한 핵심 실패는 질문을 구현 승인으로 확대 해석한 것이다. Coinglass 공식 API 연동은 “분석만”이라는 범위 수정 뒤 철회됐다. 이후 질문은 질문으로 답하고, 변경·연동 지시는 명시된 경우에만 해야 한다.
- 보고된 통계는 하나의 과거 구간, 선택된 유니버스, 잠재적 생존 편향, 불완전한 분봉·청산 데이터 및 수수료/슬리피지 가정에 의존한다. 성과 보장이나 실거래 준비 완료의 증거가 아니다.
- 토큰 노출 사고는 명시적으로 보고됐지만 회전 완료가 확인되지 않는다. 이 기록에서 가장 우선 순위가 높은 미해결 보안 항목이다. 봇 토큰이 아직 유효하다면 폐기·재발급과 저장 위치 갱신을 해야 한다. 키 값을 이 보고서에 복사하지 않는다.

6. **Hermes 범위와 Telegram 승인 동작**: 파이프라인 질의가 파일 근거를 표시하는지 확인하고, 외부 질문의 웹 검색과 파이프라인 근거 답변을 구분한다. 위험한 셸 명령이 사용자 확인 없이 실행되지 않는지 통제된 시험으로 확인한다.
7. **실거래 분리**: TOSS/Binance 주문 키가 Hermes 및 연구 컨테이너 환경에 들어가지 않는지 현재 마운트·환경 변수 이름 수준에서 확인한다. 비밀 값은 출력하지 않는다. Freqtrade가 여전히 dry-run인지 확인한다.
